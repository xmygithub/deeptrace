## 触发条件

1. 用户询问长任务 Agent 中检查点恢复与失败重试的区别
2. 用户需要为工具超时、进程中断或重复调用场景选择恢复机制
3. 用户比较 LangGraph、CrewAI、AutoGen 等框架的恢复能力

## 输入要求

1. 用户问题描述
2. 目标场景（工具超时/进程中断/重复调用）
3. 候选框架列表
4. 现有架构信息

## 步骤

1. 在工具超时场景下，优先采用带指数退避和随机抖动的失败重试，仅对只读或可靠幂等的暂时故障在单次、步骤和任务预算内有限重试；检查点恢复因回滚已完成步骤，通常不作为首选。
2. 在进程中断场景下，检查点恢复是核心手段，需持久化已完成的执行边界，使系统崩溃后无需重复工具调用、外部变更或人工审批即可继续；失败重试无法独立恢复，需依赖外部编排或检查点配合。
3. 在重复调用场景下，无论采用重试还是检查点恢复，都必须保证操作幂等性；非幂等操作在重试或恢复时会产生重复副作用（如重复计费、重复写入），且检查点恢复无法自动消除这些影响。
4. 选择生产级检查点后端（如数据库）而非内存实现，避免重启丢失状态；同时需评估检查点写入开销与恢复粒度，避免阻塞事件循环的写入方式。
5. 在公开项目选择中，LangGraph 的 checkpointer 库适合精确恢复长任务状态；CrewAI 的任务重放和流程持久化不能实现生产故障自动恢复；AutoGen 状态恢复能力相对有限，需结合具体需求评估。

## 反模式

1. 对工具超时一律使用检查点恢复，导致回滚已完成步骤、增加开销
2. 在进程中断场景仅依赖失败重试，不配合检查点或外部编排，导致无法恢复
3. 在非幂等操作上盲目重试或恢复，造成重复副作用
4. 使用内存检查点后端（如 MemorySaver）用于生产，重启后丢失状态
5. 忽略检查点排序一致性风险，如 LangGraph durability='sync' 模式可能恢复不一致状态

## 停止与降级条件
