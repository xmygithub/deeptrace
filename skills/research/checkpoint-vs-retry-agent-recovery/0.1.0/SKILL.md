## 触发条件

1. 调研长任务 AI Agent 的检查点恢复与失败重试
2. 比较工具超时、进程中断、重复调用场景下的恢复机制
3. 选择持久化执行框架或设计恢复策略

## 输入要求

1. 长任务 Agent 的步骤数、中断类型（工具超时、进程崩溃、人工审批）
2. 公开项目（如 LangGraph、AutoGen）的文档或 issue
3. 现有工作流的副作用类型（外部 API 调用、消息发送等）

## 步骤

1. 区分检查点恢复与失败重试：检查点恢复从持久化的明确状态继续，避免重复已完成的执行边界；失败重试从头开始，可能重复外部副作用。
2. 在工具调用返回前进程崩溃时，必须判断动作是否已执行，否则只能再次调用碰运气；这是最值得优先演练的故障窗口。
3. 检查点粒度以一次完整的 LLM 调用加工具调用为合理单位，且检查点必须包含足够的恢复信息（如 task_id、状态）。
4. 注意平台行为：LangGraph Cloud 中工具调用超过约 3 分钟会从最后一个检查点静默重新调度，可能导致重复执行，需评估超时与重试策略。
5. 选择框架时，根据工作流是否需要显式状态控制与持久化保证：LangGraph 使用显式状态机，AutoGen 使用对话协议，前者更适合生产级持久化。

## 反模式

1. 将会话记忆当作持久化执行：保存聊天历史不能证明哪个命令运行、哪个邮件发送或重试是否会重复副作用。
2. 忽略工具超时导致的静默重调度：在 LangGraph Cloud 中，长工具调用可能从检查点重新执行，造成重复副作用。
3. 在长任务中依赖单进程：任何中断都会迫使任务从头开始，并可能重复产生外部副作用。

## 停止与降级条件

1. 已明确区分检查点恢复与失败重试的核心区别
2. 已覆盖工具超时、进程中断、重复调用三个场景
3. 已结合至少一个公开项目（如 LangGraph、AutoGen）说明选择依据

## 验证方式

1. 验证输出是否包含：1) 检查点恢复与失败重试的定义性区别；2) 每个场景下的作用与局限；3) 公开项目选择依据；4) 所有主张均引用当前 Run 的证据 ID。

## 已知限制

1. 仅适用于 web 来源的 deep_research 模式；不覆盖 Temporal、Prefect 等项目的具体重试策略实现细节；不涉及非 web 平台。
